## 1. 执行目标与规则

先完成「打开仓库 → 查看改动 → 查看差异 → 暂存 → 提交」，再扩展历史、分支和同步，随后通过真实使用与性能验证进入发布。

功能范围以 [PRD 第 2 节](WeGit_PRD.md#2-版本范围) 为准。此计划定义实施依赖，不额外扩大版本范围，也不表示所有阶段已经完成。

- 每阶段产生可运行、可检查的交付物；基础能力用最小界面或测试入口验证。
- 取消、错误处理、风险提示和测试随功能交付，不推迟到最后一次「打磨」。
- 数据模型与服务按阶段建立，不提前实现未来所有功能和空目录。
- 涉及同一仓库写入的流程，先满足队列与恢复约束，再开放 UI 操作。
- 范围、SDK 或性能预算变化记录原因，同步修改关联文档。
- 不在缺少人员、工期和验证结果时编造交付日期；阶段开始前再估算与分配负责人。

## 19. 横向质量要求

### 19.1 Design System

随功能逐步建立 RepositoryRow、SidebarRow、BranchBadge、TagBadge、StatusBadge、DiffHeader、CommitRow、FileChangeRow、EmptyState、ErrorState 和 OperationProgress。未来组件随版本增加，不提前制造无用抽象。

间距、字号、圆角、密度、图标和动效集中维护。系统能提供的 Popover/Toolbar 优先使用系统组件，自定义 Glass 封装必须有具体场景。

### 19.2 安全与兼容

参数数组、literal pathspec、ref 验证、凭证隔离、目标重验和恢复流程从相关阶段开始执行。应用代码不借 Shell 拼接 Git 命令；关键确认不可被普通偏好关闭。

Git CLI 的存在不代表 Sandbox、SSH、Hooks、LFS、Merge Driver 或签名工具天然可用，兼容性矩阵必须写出实测版本和限制。

### 19.3 每项功能的完成定义

功能标记完成前，必须具有：

- 可用入口及符合当前版本范围的行为。
- 正确的加载、空、错误、禁用和进行中状态。
- 需要的键盘路径、焦点和可访问说明。
- 写操作的目标校验、串行、取消与恢复约束。
- 与风险匹配的验证：Parser/状态逻辑用单元测试，Git 写流程用临时仓库集成测试，交互用 UI/人工检查。
- 验证环境、结果和已知限制的记录。

简单静态文案或布局调整无需机械增加测试；涉及 Git 数据正确性与并发的修改必须有有效回归覆盖。

## 20. 缺陷分级与审查

缺陷严重程度使用 S0～S3，与产品范围的 P0 区分。

| 级别 | 示例 | 处理要求 |
| --- | --- | --- |
| S0 | 数据丢失、仓库损坏、凭证泄露、错误仓库/分支写入 | 立即停止相关发布，优先修复并复盘 |
