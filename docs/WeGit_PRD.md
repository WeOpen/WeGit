## 1. 产品定位

WeGit 面向需要频繁查看代码改动、整理提交、同步代码和管理分支的 macOS 开发者。产品围绕日常 Git 工作流组织界面，以原生交互、清晰状态、快速键盘操作和高质量差异阅读为核心价值。

核心工作流：

```text
打开或克隆仓库 → 查看改动 → 暂存 → 提交 → 获取 / 拉取 / 推送
                               ↕
                     查看历史 → 管理分支 → 处理冲突
```

目标体验是像 Finder、Xcode 和 Safari 一样自然：常用功能容易找到，复杂操作按需展开，执行前能看清影响，失败后能找到下一步。

### 1.1 产品原则

- **原生优先**：优先采用系统导航、工具栏、菜单、弹出层和设置窗口。
- **内容优先**：文件、差异和提交信息保持在同一工作上下文中。
- **键盘优先**：核心流程可通过菜单和键盘完成。
- **状态清楚**：始终显示当前仓库、分支、改动和正在执行的操作。
- **兼容 Git**：以实际 Git 仓库和工作区为事实来源，不维护另一套 Git 真相。
- **性能可验证**：大型历史分页加载，差异按需解析，Git 和重计算不阻塞界面。
- **风险明确**：说明操作对象、影响范围和恢复限制，避免误操作。

### 1.2 目标用户

核心用户包括 macOS、iOS、Web、后端和独立开发者，以及希望减少 Git 命令输入的初中级用户。高级用户需要精确的部分暂存、提交图、可追溯命令记录和逐步完善的 Rebase、Stash、Reset 等能力。

### 1.3 非目标

首版不包含完整代码编辑器、IDE、云端 Git 托管、Issues/Projects 管理、CI/CD 控制台、团队文档或内置 AI Agent。未来 Hosting Provider 和 AI 能力独立扩展，不影响本地 Git 工作流。

## 3. 核心用户场景与验收

| 场景 | 预期结果 |
| --- | --- |
| 整理一次普通提交 | 在 Changes 页面查看差异、暂存目标内容、填写消息并提交，无需切换页面 |
| 只提交部分改动 | 提交只包含暂存区内容，未暂存内容完整保留，提交后正确更新计数 |
| 首次使用远程仓库 | HTTPS/SSH 克隆完成后打开仓库；失败时说明原因和重试方式 |
| 查看历史与合并关系 | 提交图清楚表达父子关系和 Merge；详情对应选中提交及比较基准 |
| 分支同步 | 显示远端、目标分支和上游；领先/落后状态注明来自最近一次 Fetch |
| 发生合并冲突 | 显示操作类型与冲突文件；用户可外部编辑、标记解决、继续或中止 |
| 同时使用 Terminal | 外部修改在事件稳定后自动反映；旧请求不覆盖新仓库或新状态 |
| Git 命令失败 | 保留草稿与选择，提供可理解错误、脱敏详情及适用的恢复操作 |

「1～3 次操作」只用于衡量已有上下文中的高频操作，不包含打开文件、编辑代码、输入提交消息、网络认证或危险操作确认。以已选择文件且消息已填写为起点，普通「暂存 → 提交」应在 3 次交互内完成。

## 4. 信息架构与主窗口

主布局为 Sidebar、对象列表、详情三栏；可选 Inspector 是附加元数据面板，不替代差异或提交详情。

| 区域 | 职责 |
| --- | --- |
| Toolbar | 仓库与分支切换、Fetch/Pull/Push、搜索、活动与辅助面板 |
| Sidebar | Changes、History、Branches 等导航；只显示当前版本可用模块 |
| 对象列表 | 文件、提交、分支及后续的 Stash/Tag |
| 详情 | 差异、提交详情、分支详情及后续冲突编辑器 |
| Commit Composer | Changes 内容区底部的提交输入与操作 |
| Inspector | 选中对象的可选摘要、元数据和辅助操作 |

采用 `NavigationSplitView` 和系统工具栏。Liquid Glass 用于系统导航与控制层；差异代码、提交列表和提交图使用稳定、可读的内容背景。尺寸、快捷键和交互细节见 [UI/UX 规范](WeGit_UI_UX_Spec.md)。

## 5. 仓库管理（R01）

### 5.1 打开与恢复

支持文件夹选择、拖入和最近仓库入口。保存名称、位置、最近打开时间、收藏状态及必要的访问书签；分支和 Remote 等 Git 信息以重新读取为准。

必须处理目录移动、权限丢失、书签过期、非仓库目录、未诞生分支和 Detached HEAD。删除最近记录只删除应用记录，不删除仓库文件。

提供 Reveal in Finder、Open in Terminal、Copy Path；有适用 Xcode 项目或可打开对象时提供 Open in Xcode。

### 5.2 克隆

输入 Repository URL、目标父目录和文件夹名称，支持 HTTPS 与 SSH，包括常见的 SSH SCP 风格地址。校验地址、Git 可用性、目录和写权限，不接受带明文密码或 Token 的地址进入持久化记录。

克隆展示当前阶段、可获得的进度及传输信息。没有可靠百分比时使用不定进度。认证失败、网络断开、磁盘不足和取消均须可恢复；清理仅限本次操作创建的目录，并经用户确认。不得删除预先存在的用户目录。

浅克隆、递归 Submodule 等高级创建选项随对应后续能力评估，不作为 P0 入口。

## 6. Changes 与暂存管理（R02、R04）

### 6.1 分组与状态

分组顺序为「冲突、已暂存、未暂存、未跟踪」。同一文件可以同时出现在已暂存和未暂存分组，分别对应不同差异。总改动数按唯一路径计数，不能直接把分组数量相加。

| 状态 | 标识 | 含义 |
| --- | --- | --- |
| 修改 | `M` | 已跟踪文件内容变化 |
| 新增 | `A` | 已加入暂存区的新文件 |
| 删除 | `D` | 文件删除 |
| 重命名 | `R` | 原路径与新路径同时可见 |
| 复制 | `C` | 解析结果识别为复制时展示 |
| 未跟踪 | `?` | 尚未加入暂存区的文件 |
| 冲突 | `U` | 存在未合并的索引项，附「冲突」文本 |
| 类型变化 | `T` | 文件类型变化，例如普通文件与符号链接变化 |

标识、可读文本和颜色共同传达状态；不得只依赖颜色。筛选不能改变 Stage All 等操作的隐含范围：默认「全部」指当前仓库的全部适用文件，若只操作筛选结果必须另行标明。

### 6.2 暂存规则

- 文件与差异块操作必须与当前显示层一致，已暂存区执行 Unstage，未暂存区执行 Stage。
- 暂存不自动提交；提交不自动加入未暂存或未跟踪文件。
- Stage All 不替用户把未解决冲突标记为解决。
- 差异已变化时停止块级操作并要求刷新，不根据过期视图继续应用。
- 二进制、特殊文件或不能可靠构造补丁的变更，只提供文件级操作并说明原因。
- 未诞生分支必须支持取消暂存，不能假设 `HEAD` 已存在。

### 6.3 丢弃规则

确认界面说明文件、范围和恢复限制。默认文件级 Discard 仅还原未暂存改动到暂存区内容；若要同时清除已暂存内容，必须作为独立操作说明。未跟踪文件的删除与已跟踪文件还原分开处理，优先使用废纸篓。

未提交内容不保证可通过 Reflog 恢复，不得统一承诺「可撤销」。

## 7. 差异视图（R03）

P0 支持 Unified/Split、旧/新行号、增删标识、差异块、语法高亮、上下文折叠与按需展开、忽略空白、词级差异、复制行/选区和前后差异导航。

首批语法高亮目标覆盖 Swift、Objective-C、JavaScript、TypeScript、HTML、CSS、JSON、YAML、Markdown、Python、Java、Kotlin、Go、Rust 和 Shell。未知语言或高亮失败时回退为纯文本，不影响差异正确性。

每个视图必须注明比较基准：

- 未暂存：工作区相对暂存区。
- 已暂存：暂存区相对 HEAD；首个提交前相对空树。
- 提交详情：选中提交相对指定父提交；根提交相对空树。
- Merge 提交：默认相对第一父提交，提供父提交选择，不能伪装成唯一的合并差异。
- 未跟踪：作为待添加内容预览，不能因常规 `git diff` 无输出而显示「无改动」。

忽略空白和词级差异只影响阅读；用于 Stage/Discard 的补丁必须来自未经视觉转换的原始差异。必要时禁用块级操作并提示切回可操作模式。

P0 对二进制显示类型、大小与可用的外部打开入口；PNG、JPEG、WebP 的 Before/After 对比保留为 v1.1.x / v1.2 候选，尚未作为 v1.1 必选交付。大差异先显示摘要并允许显式加载，操作需可取消且有内存上限。

## 8. 提交（R05）

Commit Composer 提供标题、可选描述、Amend 和 Commit & Push。支持紧凑输入布局，输入草稿按仓库保留；消息历史保留为 v1.1.x / v1.2 小项候选。

| 情况 | 行为 |
| --- | --- |
| 普通提交 | 消息有效、有已暂存内容、无未解决冲突且无互斥操作时可执行 |
| Amend | HEAD 存在且无冲突/进行中序列操作时可执行；允许只修改消息，无需新增暂存内容 |
| 完成 Merge | 冲突索引已清空且满足 Git 状态要求时可以创建合并提交，不套用普通提交的空暂存限制 |
| 正在提交 | 禁止重复点击，显示状态，保留消息 |
| Hook 或签名失败 | 保留草稿，显示原因和详情；不自动跳过 Hook 或签名 |
| Commit 成功、Push 失败 | 分别报告结果，允许只重试 Push，不重复创建提交 |

Amend 会生成新的提交，需说明是否可能改写已发布历史。已有 Git GPG/SSH 签名配置在 P0 中被尊重；应用不能完成认证或签名交互时应清楚报错，不静默降级为未签名提交。专门的签名配置和按钮为后续候选，先补真实交互及失败路径证据。

提交成功后刷新状态、历史和分支引用。只提交部分内容时，工作区可以继续存在改动；Push 只改变同步状态，不会使工作区自动变干净。

## 9. 历史与提交详情（R06）

历史列表显示提交图、消息、引用徽标、作者和时间；领先/落后是分支状态，不是每个提交的独立属性。默认浏览范围为本地分支、远端跟踪分支、Tag 和 HEAD，可切换为当前分支。

提交图必须表达节点、父子关系、分支线、合并线和 HEAD。首批最多加载 200 个提交，后续分页；浅克隆和分页边界须区分，不把未加载的父提交画成根提交。

详情包括完整/短 SHA、作者和提交者、各自时间、父提交、指向该提交的分支/Tag、改动文件和增删统计。「指向该提交的分支」与「包含该提交的分支」不能混用。

P0 操作包括复制 SHA、检出提交、新建分支、查看父提交差异。检出提交前说明 Detached HEAD；新建分支可作为替代入口。Tag、Cherry-pick、Revert、Reset、扩展比较和多提交批量操作按后续版本逐步提供。

## 10. 分支与合并（R07）

本地和远端跟踪分支分组展示，包含当前标记、上游、领先/落后和最近提交。无上游时显示「未设置上游」，不得显示为零领先/零落后。

创建分支输入名称、起点和是否立即切换。名称通过 Git 规则验证，检查已存在引用；从远端跟踪分支切换时明确将创建哪个本地分支及上游。

切换遇到会被覆盖的本地改动时，提供取消、查看受影响文件和提交建议。Stash & Checkout 在 V1.1 后提供；P0 不自动储藏或丢弃。

Merge 界面明确「将来源分支合并到当前分支」，显示源、目标和工作区状态。执行时重新验证当前分支和引用，不能只依赖打开弹窗时的状态。普通合并优先使用既定策略；强制创建合并提交属于明确的高级选项。

删除分支前检查当前分支、未合并提交和其他 Worktree 占用，说明删除的是本地分支还是远端分支。P0 提供本地分支删除，远端分支删除不作为首版要求。

## 11. 远程同步与认证（R08）

Fetch 更新本地远端跟踪引用；Pull 获取并整合改动；Push 将提交发送到明确的远端引用。每次写入均显示目标仓库、Remote 和分支，不根据模糊名称推断目标。

Pull 提供 Merge、Rebase 和 Fast-forward Only 策略。优先显示有效 Git 配置；没有明确配置时建议 Fast-forward Only，并让用户选择分叉时的整合方式。不得悄悄改写用户的全局 Git 配置。

`main ↑2 ↓1` 表示相对于已知上游领先 2 个、落后 1 个提交；网络未刷新、无上游和读取失败必须有不同状态。

Force Push 默认只提供 `--force-with-lease`：确认框说明远端、目标引用、历史覆盖风险和预期远端提交。确认后远端已变化则拒绝并刷新。普通 `--force` 不进入 P0 界面。

认证优先复用 Git Credential Helper、系统 SSH、SSH Agent 和 Keychain。应用自己持有的敏感信息必须存入 Keychain，不进入 UserDefaults、SwiftData、普通配置或日志。不复制 SSH 私钥；不绕过 SSH 主机身份检查。

## 12. 冲突和进行中操作（R09）

P0 的基础冲突闭环是 Merge 和 Pull Rebase 的前置要求，不能延期到内置编辑器上线后才提供。

1. 显示当前操作类型、涉及分支和未解决文件数。
2. 提供外部编辑器/Finder/Terminal 入口，二进制、删除/修改、重命名冲突须给出适用说明。
3. 用户检查结果后显式「标记已解决」，由 Git 索引的未合并项判断是否全部解决。
4. 全部解决后按实际操作提供 Continue Merge 或 Continue Rebase；仍可能遇到下一轮冲突。
5. 中止前说明会撤回哪些操作中改动；失败时保留现状和诊断，不强制 Reset。

检测到外部 Cherry-pick/Revert 等未支持序列操作时，P0 保持状态可见，限制不兼容写入并引导在 Terminal 完成；应用内执行与继续/中止从 v1.1 后移至 v1.2 需求池，按完整恢复闭环验收。

V1.2 的内置编辑器提供 OURS/THEIRS/RESULT、接受一侧、按块编辑和保存。标签必须说明实际来源；Rebase 中两侧语义不同，不能总把 OURS 解释为「我的分支」。Accept Both 只是文本组合，不代表业务逻辑正确。

## 14. 搜索、设置与原生能力（R11、R12）

### 14.1 搜索和命令

P0 的搜索作用域是当前仓库。提交搜索覆盖消息、SHA、作者，文件搜索默认是路径筛选，不暗示全文代码搜索。加载范围内过滤与完整历史查询必须标明区别；查询更新取消旧任务，旧结果不能覆盖新查询。

命令面板提供打开/克隆仓库、分支切换、新建分支、Fetch/Pull/Push、设置和页面导航。禁用命令解释原因；危险命令仍走正常确认流程。快捷键统一采用 [UI/UX 第 19 节](WeGit_UI_UX_Spec.md#19-键盘与菜单)，不在其他文档重复定义。

### 14.2 设置

| 类别 | P0 范围 |
| --- | --- |
| General | 默认仓库位置、启动行为、窗口恢复、可配置的普通确认 |
| Git | 可执行文件、版本和能力、用户身份、默认分支、Pull/Merge 策略 |
| Appearance | System/Light/Dark、紧凑/舒适密度、文件图标、差异字体与字号、可关闭的界面动效 |
| Diff | Unified/Split、空白显示、上下文行数、词级差异、行号 |
| Commit | Amend 确认和草稿行为；显式签名配置入口按后续候选评估 |
| Advanced | 活动日志保留、诊断、重置应用界面状态 |

Git 配置编辑必须显示「全局」或「当前仓库」作用域和有效值来源。不可关闭丢弃、强制推送等关键风险确认。Accounts 在 Provider 功能上线时增加，不在 P0 显示空页面。

### 14.3 可访问性与窗口

适配浅色/深色、减少透明度、减少动态效果、增强对比度、VoiceOver、完整键盘访问和字号调整。窗口恢复尺寸、位置、分栏宽度、仓库和页面；恢复对象已不存在时回到有效状态。

## 15. 可靠性、活动与恢复

- 同一仓库的 Git 写操作必须串行执行，包括 Fetch；读取操作有并发上限并与写入协调。
- 外部修改通过文件事件合并刷新，并提供手动刷新和恢复焦点后的校验。
- 操作面板显示等待、运行、成功、失败、取消和需要用户处理；取消不等于回滚。
- 错误必须包含发生了什么、影响范围、可用的下一步和脱敏详情，不能只有退出码。
- Activity Log 展示实际命令摘要、仓库、时间、耗时和结果，输出经过脱敏并限制体积。
- 能记录提交恢复点的操作保存相关 SHA；未提交内容恢复、已删除文件恢复和远端历史恢复分别说明限制。
- 应用设置和缓存不是 Git 状态的事实来源；刷新失败不得把旧状态伪装成已刷新成功。
- 默认不上传代码、差异、提交消息、路径或凭证。若加入遥测，采用明确告知和选择加入，并提供关闭与删除方式。

## 16. 性能目标与测量口径

以下是初始预算，尚未实测。Phase 0 固定基准设备和工具链，Phase 12 使用同一套 fixture 验证；调整预算必须记录原因与证据。

| 指标 | 初始目标 | 测量边界 |
| --- | --- | --- |
| 冷启动 | 主窗口出现 < 1 s | 进程启动至可交互窗口，不含首次授权或安装工具 |
| 仓库外壳 | < 500 ms | 选择有效且已授权仓库至外壳可交互，Git 数据可继续加载 |
| 普通仓库状态 | < 300 ms | 状态请求至解析完成并发布 UI 快照 |
| 普通文件差异 | 首屏 < 150 ms | 选择文件至首屏差异可读，含 Git、解析与渲染 |
| 历史首批 | 200 个提交 < 300 ms | 请求至提交列表和图首屏可用 |
| 外部状态更新 | 事件稳定后 < 1 s | 普通 fixture 下，事件到新状态显示；不含持续外部写入 |
| 滚动 | 60 fps 目标 | Diff/History 固定滚动场景；ProMotion 120 Hz 为优化目标 |
| 大型仓库 | 100,000+ 文件、100,000+ 提交可用 | 独立压力场景；不直接套用普通仓库的延迟预算 |

建议普通 fixture 使用约 1,000 个已跟踪文件、1,000 个提交、20 个改动文件；普通差异为不超过 1,000 行、200 KB 的文本文件。最终 fixture 在实现时固定并记录生成方式。

本地指标使用 Release 构建，记录设备、系统、Git 版本、仓库规模、缓存冷热、至少 30 次采样的中位数与 P95；上述延迟预算以 P95 判断。网络操作另记录网络条件和服务端耗时，不承诺统一完成时间。大型仓库需记录内存峰值、长任务与取消响应，不能仅以「没有崩溃」作为通过标准。

## 17. 发布验收

V1.0 以 R01～R13 的 P0 列和 [执行计划](PLAN.md) 的发布检查为准：

1. 核心提交闭环、克隆与远程同步能在真实临时仓库完成。
2. 部分暂存、未诞生分支、Detached HEAD、脏工作区和冲突处理结果正确。
3. 提交图与实际父子关系一致，提交差异比较基准明确。
4. 外部变更和取消后能重新读取权威状态，不出现错误仓库或错误分支写入。
5. 无已知数据丢失、凭证泄露、仓库损坏或阻塞核心流程的问题。
6. 键盘、深色模式、最小窗口及可访问性检查通过。
7. 性能目标附测试结果；未达标项必须明确修复或重新评审，不以设计数字代替证据。

产品成功首先体现为核心流程可靠、差异阅读清楚、日常操作自然；高级功能按后续版本验收，不用于扩大首版发布范围。
