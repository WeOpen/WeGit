控件高度不是靠目测，而是把 `DesignSystem` 源码编进一个探针程序，塞进真实 `NSWindow` 的 `NSToolbar`（`titlebarAppearsTransparent` + `.unified`），与系统 `.toggleSidebar` 同排，整窗 `cacheDisplay` 后逐行比色，读出绘制像素高度：

| 控件 | 首轮（30pt 定值） | 本轮 |
| --- | --- | --- |
| 系统侧栏折叠按钮（参照） | 单元格 36.0、绘制 34.5 | 单元格 36.0、绘制 35.5 |
| 工具栏 pill（获取 / 拉取 / 推送） | 单元格 42.0、绘制 39.5 | 单元格 36.0、绘制 35.5 |
| 菜单（获取 / 更多） | 绘制 33.0 | 绘制 35.5 |
| 圆形图标按钮（刷新 / 搜索 / 检查器 / 取消） | 绘制 29.5 | 绘制 35.5 |
| 无障碍 `.bordered` 分支（降低透明度 / 增强对比度） | 绘制 22 左右 | 绘制 35.5 |
| `.small` 行内圆钮 | 26 | 26（未改） |
| `.mini` 紧凑圆钮 | 24 | 24（未改） |
| `.large` 欢迎页按钮 | 34 | 34（未改） |

绘制值比标称内框大约 1pt，因为边缘抗锯齿行也算作不同像素；同一轮内的数值可以直接相比，跨轮次只能看趋势。

两处关键关系决定了这一轮的写法。一是玻璃按钮：在工具栏单元格里，不固定 label 高度时系统会直接给到 36pt 单元格，绘制 34.5；一旦把 label 钉到 `30 − 8 = 22`，单元格反而被撑到 42pt，绘制 39.5——所以工具栏路径必须**放弃**钉高，而窗口内控件仍沿用「目标高度减系统玻璃内边距（mini 2 / small 6 / regular 8 / large 12）得到 label 高度」的老约定。二是玻璃菜单：`.glassEffect` 胶囊按 `frame − 1.5` 绘制（实测 frame 34.0 → 32.5、34.5 → 33.0、35.0 → 33.5、36.0 → 34.5、37.0 → 35.5），所以想要 34.5 的表面必须给 36 的 frame，给 34.5 会少 1.5。菜单绘制高度不受 `icon:` 开关影响，只由 frame 决定。

首轮把三族控件统一到 30pt 的做法被否决，原因也在这里：30pt 是窗口内控件的约定，工具栏里的参照物是系统折叠按钮，不是 `AppStyle.controlHeight`。因此新增 `AppStyle.toolbarControlHeight = 36` 只服务于工具栏，`controlHeight` 仍是 30，`WorkbenchGlassTabs`、`GlassSegmentInteraction`、`GlassCapsuleSurface`、欢迎页与行内小按钮全部未动。

主题检查原先断言「内置 Light/Dark 的 canvas 与 chrome 取同一个原生底色」。这条约定正是 P0-1 要推翻的，按新梯度改写为结构断言而非删除：四个表面必须互不相同，且侧栏是最暗（凹陷）一档、卡片是最亮（抬升）一档。两条窗口底色断言同步由 `.canvas` 改为 `.chrome`，与 `ThemeWindowProbe.apply()` 的实际取值一致——过去两者相等所以断言碰巧成立，现在分开后必须显式写对。
